## 2. Индексация и поиск корпуса Ponomar

### 2.1. Проблема

| Параметр | Значение |
|----------|---------|
| Число XML-файлов | ~28 959 |
| Размер corpus (несжатый) | ~184 МБ |
| Лимит Firebase Functions 1st gen | 100 МБ сжатый / 500 МБ несжатый |
| Текущий риск | Corpus + code приближается к лимиту |
| Runtime-накладные расходы | `fs.existsSync` на каждый файл при каждом запросе |

### 2.2. Решение: manifest + lookup index

**Принцип:** index.json генерируется один раз (CI / вручную), загружается в RAM
на cold start, `fs.existsSync` заменяется на `Set.has` из индекса.

### 2.3. Структура файлов

```
functions/
  src/
    ponomar/
      indexLoader.ts    ← загружает index.json, предоставляет fileExists()
  ponomar/
    index.json          ← главный манифест runtime  (~5.8 МБ, 28 959 записей)
    index.ndjson        ← построчный JSON для grep/jq  (не деплоится, см. §2.7)
    index.version       ← строка версии (timestamp)

scripts/
  buildPonomarIndex.js  ← Node.js генератор; node scripts/buildPonomarIndex.js
```

### 2.4. Схема записи `index.json`

```json
{
  "id":    "menaion-en-06-23",
  "lang":  "en",
  "cycle": "menaion",
  "date":  "06-23",
  "path":  "en/xml/06/23.xml",
  "size":  234,
  "mtime": "2026-06-01T12:00:00Z"
}
```

Дополнительные поля (если нужны): `cId`, `nday`, `sha256` (с флагом `--sha256`).

### 2.5. Три уровня индекса в памяти runtime

| Структура | Ключ | Операция |
|-----------|------|---------|
| `_pathSet: Set<string>` | `path` | O(1) `has()` — заменяет `fs.existsSync` |
| `_livesByLang: Map<lang, Set<cId>>` | lang-код | O(1) — «есть ли жизнь у cId в языке?» |
| `_menaionByLang: Map<lang, Set<date>>` | lang-код | O(1) — «есть ли день ММ-ДД для языка?» |

### 2.6. Runtime-поведение (indexLoader.ts)

1. **Cold start**: `loadIndex()` вызывается при первом обращении (lazy init).
2. `index.json` (~5.8 МБ) парсится один раз, заполняет `_pathSet`.
3. Все дальнейшие `fileExists(absPath)` — O(1) по Set.
4. Если `index.json` недоступен или некорректен → `isIndexReady() = false`,
   `xmlLoader.ts` автоматически деградирует до `fs.existsSync`.
5. **Cache invalidation**: не реализована (instance recycled по Firebase), при
   пересборке индекса достаточно передеплоить функцию.

### 2.7. Генератор `scripts/buildPonomarIndex.js`

```bash
# Быстро (без sha256):
node scripts/buildPonomarIndex.js

# С контрольными суммами (~30 с):
node scripts/buildPonomarIndex.js --sha256
```

Выходные файлы:
- `functions/ponomar/index.json` — коммитится, деплоится вместе с функциями
- `functions/ponomar/index.ndjson` — добавить в `.gitignore`/`firebase ignore` (только для tooling)
- `functions/ponomar/index.version` — коммитится

### 2.8. Когда выносить XML в Cloud Storage

Если `firebase deploy` упирается в лимит 100 МБ compressed:

1. Загрузить XML в GCS bucket (`gs://{project}-ponomar/`)
2. В репо оставить только `index.json` + код
3. В `xmlLoader.ts` заменить `fs.readFileSync(path)` на
   `Storage.file(relPath).download()` + кэш в `/tmp`
4. `fileExists(path)` продолжает работать через `indexHasFile()` без изменений

## 3. Аудит системных слепых зон — WebTypikon Firebase Edition v4.0

> Источник: внешний аудит пайплайна с 12 этапами и советом 24 специалистов.  
> Цель: ликвидировать структурные уязвимости до перехода в продакшн.

### 3.1. Ключевые слепые зоны

#### 3.1.1. Неполная реализация этапов 5–11

Этапы 1–4 и 12 детально описаны и частично реализованы. Этапы 5–11 содержат логику в состоянии «стаба»: Matins, Hours, Liturgy, Holy Week, Paschal-блоки описаны структурно, но часть проверок и Firestore-записей помечена как «awaiting implementation». Это создаёт риск: система выглядит работающей, но многие пути в ней не проходят реальную валидацию.

#### 3.1.2. Уязвимости npm / Cloud Functions

~~В логах фиксируются сбои `Cannot find module 'uuid'` и `Cannot find module 'xml2js'`.~~ **Устранено:** код перешёл на `fast-xml-parser` (bundled dependency); `uuid` и `xml2js` из кода удалены. Текущие риски loader'а описаны в §3.4.2.

#### 3.1.3. Отсутствие сквозных тестов

Нет систематической end-to-end регрессии даже по базовым датам (обычный будний день, Великий праздник, Bright Week, Pentecost, All Saints). Это оставляет огромную область «невидимых» ошибок. Любое изменение логики подавления или source-priority создаёт риск регрессии без обнаружения.

#### 3.1.4. Слабая наблюдаемость

Главный канал контроля — email-нотификатор и console-логи. Нет структурированных метрик: количество элементов, доля fallback, число SUPPRESSED/BLOCKED, время сборки по этапам. Системные сбои (например, целые языковые подпапки не загружены) обнаруживаются только через точечные репорты.

#### 3.1.5. UX «совета» и пользовательских коррекций

Действия правого клика (① doubt, ② error, ③ why, ④ alternative, ⑤ report) описаны концептуально, но не реализованы как целостный UX-поток. Разделение ответственности между Specialist 13 (Translation Agent) и Specialist 14 (Corrector) пользователю непрозрачно: непонятно, что происходит после «report» или «doubt».

#### 3.1.6. Сложность source-priority и suppression

Многоуровневая логика (PENTECOSTARION → OCTOECHOS → MENAION → HOROLOGION) плюс правила подавления (Prayer of St Ephraim, Dogmatikon, Bright Week Hours, Compline at Vigil, Magnificat на праздниках, Litia TRADITIONSPECIFIC) — при такой сложности возникают «suppression leaks»: элемент одновременно BLOCKED и присутствует в выводе, или флаг срабатывает там, где не должен.

#### 3.1.7. Языковая матрица покрыта неполностью

`langMatrix` для EN/CU/RU/EL/FR/ZH заложена, но многие элементы (Triune Canon, Pentecostarion-специфика, Holy Week уникальные службы) отсутствуют в части языков. В UI нет явного разграничения «UNTRANSLATED» / «FALLBACK из CU» / «NOTEXTAVAILABLE», хотя Stage 12 прописывает fallback-цепочку.

4. Следуем православной традиции Типикона и используем только тексты из Ponomar-корпуса.
```

#### 3.4.2. Стабильность Ponomar loader — статус и правила

**Исторический контекст (устаревший):** TZ ранее упоминала сбои `Cannot find module 'uuid'`
и `Cannot find module 'xml2js'`. Эти модули давно удалены из кода. Текущий loader
использует `fast-xml-parser` (bundled dependency) и не требует `uuid`.

**Текущее состояние loader'а (2026-06-23):**

| Компонент | Статус | Примечание |
|-----------|--------|------------|
| `indexLoader.ts` — index.json | ✅ работает | 28 959 записей, O(1) lookup; fallback на `fs.existsSync` если индекс недоступен |
| `xmlLoader.ts` — XML parsing | ✅ работает | `fast-xml-parser`, graceful return `null` при ошибке парсинга |
| `fileExists()` — проверка файла | ✅ работает | index → `fs.existsSync`, двухуровневый fallback |
| `loadSaintData` — 3-step fallback | ✅ работает | own-lang → CU/RU fallback → missingInCorpus |
| Health check / metrics | ❌ нет | нет endpoint'а, нет счётчиков corpus miss/hit |
| Integration test (prod) | ❌ нет | тесты проверяют локальный корпус, не production Firebase |
| Silent error swallowing | ⚠️ риск | `.catch(() => null)` маскирует ошибки Firestore — невидимо в логах |

**Реальные текущие риски (в порядке приоритета):**

```
РИСК 1 (HIGH): Нет health-check endpoint'а.
  Нет способа убедиться, что corpus доступен в production-среде Firebase
  до начала реальных запросов. При превышении лимита размера пакета
  (~500 МБ unsized) часть XML-файлов может быть truncated — тихо, без ошибок.

РИСК 2 (MEDIUM): Silent fallback без метрик.
  Когда loader падает в fallback (corpus miss → empty result), функция
  возвращает hasReadings=false или missingInCorpus=true без записи в лог.
  Нельзя отличить "файла нет в корпусе" от "файл есть, но не прочитан".

РИСК 3 (MEDIUM): Синхронные disk reads на каждый запрос.
  `fs.readFileSync` для 5–15 XML-файлов на каждый composeService().
  На cold start с холодным диском может дать 2–5 сек дополнительной задержки.

РИСК 4 (LOW): index.json vs. реальные файлы могут расходиться.
  Если corpus обновился без пересборки индекса, fileExists() вернёт false
  для существующих файлов. Fallback на fs.existsSync поймает это, но медленнее.
```

**Правила для Claude при работе с Ponomar loader:**

```
L1. Не добавлять новые синхронные readFileSync в hot path без кэширования.
L2. Любой новый corpus-lookup должен: (a) использовать fileExists(), (b) обернуть
    XML.parse() в try/catch, (c) возвращать null/empty при ошибке.
L3. Перед prod-деплоем — запустить B5 (Ponomar health check) и убедиться,
    что все эталонные пути доступны в Firebase environment.
L4. Не считать ".catch(() => null)" достаточной обработкой ошибки Firestore —
    добавлять console.error() с контекстом для видимости в Cloud Logging.
L5. При добавлении новых XML-путей — пересобирать index.json
    (`node scripts/buildPonomarIndex.js`) и коммитить новый index.
```

#### 3.4.3. Общие правила разработки

```
1. Новые suppression-правила обязательно содержат typikonReference.
2. Изменения JSON-схемы документируются для возможности Firestore-миграции.

3. Диакон всегда правее священника (или на `altar_left`/`solea_right`).
4. Предметы помещаются в слот `altar_top_center` (над престолом) или рядом с ролью.
5. Один и тот же шаблон сцены используется для повторяющихся моментов службы.

### 4.7. UX — галерея и модальное окно

### 4.8. Формат изображений

- Размер: 16:9, минимум 800×450 px.
- Стиль: минималистичный плоский вектор, вид строго сверху.
- Цвета: светло-бежевый фон, золотой для облачений и предметов, красный для антиминса/фелони.
- Без текста, без UI-элементов, без перспективы.
- Формат: JPG (или PNG/WebP при прозрачности).
