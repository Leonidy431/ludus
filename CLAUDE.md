## 🛑 ТАБУ №0 (ВЫШЕ ВСЕХ): КОНСТИТУЦИЯ ПРОЕКТА — DEMIURGIC CAUSALITY

**Дата:** 2026-09-28  
**Приоритет:** ВЫШЕ ВСЕХ ОСТАЛЬНЫХ ПРАВИЛ  
**Статус:** ФУНДАМЕНТАЛЬНЫЙ — не может быть изменён без явного разрешения

---

### Формулировка Конституции

Ludus — это **теологическая ролевая система**, где каждая сущность (персонаж, NPC, локация, система) подчиняется принципу **Demiurgic Causality**:

```
ФОРМА (Attributes) → ДЕЙСТВИЕ (Behavior) → ЦЕЛЬ (Spiritual Teaching)
```

**Это означает:**

1. **ФОРМА (Attributes):** Каждый персонаж/NPC имеет набор атрибутов (Wisdom, Faith, Dexterity, Constitution, Charisma, Cunning, Erudition), которые определяют его онтологический статус в сотворённом мире.

2. **ДЕЙСТВИЕ (Behavior):** На основе ФОРМЫ выполняются действия — диалоги, выбор пути, боевые решения, молитвы. Действие должно быть логическим следствием ФОРМЫ.

3. **ЦЕЛЬ (Spiritual Teaching):** Каждое действие ведёт к духовному обучению (через диалоги с NPCs, решение загадок, достижение knowledge gates). ЦЕЛЬ — освещение (theoria).

---

### Правило решений: Конституция в каждом решении (оператор, 2026-09-30)

**Решение оператора (дословно):** «Следуй конституции игры в решениях и так далее. Это правило табу и выше».

1. **Каждое решение проверяется Конституцией** — код, сцена, механика, данные, звук, интерфейс, порядок работы. Проверка — одна строка в HLD или в описании решения: «Конституция: ФОРМА … → ДЕЙСТВИЕ … → ЦЕЛЬ …».
2. **Решение без такой строки не принимается.** Если строку нельзя написать, значит у механики нет учительной цели; её не делают или переделывают.
3. **Конституция выше всех табу, в том числе выше ТАБУ №0.01 (APK).** APK — порядок работы, Конституция — закон содержания. Если требование сборки спорит с Конституцией, побеждает Конституция, а сборка ждёт.
4. Проверяются и запреты Конституции: ровно 7 атрибутов, никакой случайности в наградах, врата — диалог, атрибут и действие вместе.

## 🛑 ТАБУ №0.01: СБОРКА APK ДЛЯ ШЛЕМА — ПРИОРИТЕТ; КАЖДАЯ ЗАДАЧА ДОПОЛНЯЕТ APK (оператор, 2026-09-30)

**Приоритет:** выше всех табу, кроме Конституции (ТАБУ №0) и правила решений при ней: Конституция — закон содержания, это правило — о порядке работы.

**Решение оператора (дословно):** «Дополняй сборку apk шлема это приоритет и правило Клауд мд выше и табу».

1. **Итог задачи — в APK.** Задача закончена, когда её результат есть в APK для Quest 3 (сцена, данные или звук в `godot/`), а не только в веб-версии или в документе. Если сделано только для веба, следующий шаг — перенос в Godot.
2. **Сломанная сборка APK — стоп-линия.** Красное задание `android` в `.github/workflows/godot.yml` чинится раньше любой другой работы.
3. **APK ставится поверх прежнего.** Номер версии растёт с каждой сборкой, ключ подписи постоянный. Иначе шлем откажется обновлять игру, и её придётся удалять вместе с сохранениями.
4. **APK легко взять.** Сборка из `main` выкладывается в GitHub Release `headset-latest` вместе с контрольной суммой SHA-256. Артефакт прогона остаётся для веток.
5. **Опись «веб → шлем».** `docs/APK_PARITY.md` перечисляет, что есть в веб-версии и чего ещё нет в APK. Каждая задача сокращает этот список или объясняет, почему пункт в шлем не идёт (например, текстовая версия Webtypikon).
6. **Честность.** Зелёная сборка доказывает только сборку. «Проверено в шлеме» говорит оператор (ТАБУ №0.02 п. 4).

## 🛑 ТАБУ №0.011: РЕВИЗОР ЛИМИТОВ APK — ВЕЗДЕ, В КАЖДОЙ ЗАДАЧЕ (оператор, 2026-09-30)

**Приоритет:** выше всех табу, кроме Конституции (ТАБУ №0) с правилом решений при ней; действует вместе с ТАБУ №0.01 как его проверка. Конституция — закон содержания, ТАБУ №0.01 — порядок работы, это правило — мера: сколько шлем может унести.

**Решение оператора (дословно):** «оцени лимиты APK и шлема по мегабайтам нагрузки на память итд. сделай ревизор агента и требования к APK МД-ревью Ф1»; «собранного ревизора по лимитам APK применяй везде, это правило клауд мд выше и табу».

**Где что лежит:**
- требования и бюджеты (лимиты Quest 3 и Meta с источниками, текущие значения, запас, чем проверяется) — `docs/APK_REQUIREMENTS.md`, машинная часть — `godot/data/apk-budgets.json`;
- ревизор — агент `.claude/agents/apk-revisor.md` (только читает и перемеряет, код не правит);
- ворота CI — `scripts/godot/check_budgets.py`: `--tree` в задании `test`, `--apk` в задании `android` по готовому APK;
- МД-ревью — `docs/review/МД_РЕВЬЮ_APK_Ф<N>_<дата>.md`.

1. **Везде.** Каждая задача, фаза HLD, слияние ветки агента, ежечасный цикл и PR, который трогает `godot/`, `public/vr/`, данные или модели, проходит ревизора лимитов APK до того, как называется готовой.
2. **Формат МД-ревью** — по образцу оператора: одна строка-вердикт «МД-ревью Ф<N>: <что добавлено, с числами>. Проверено, что …; исправлено …», затем таблица бюджетов «до → после», блокеры и что можно измерить только в самом Quest 3.
3. **Дельта в каждом PR.** Описание PR называет прирост APK (МБ) и бюджетов сцены (треугольники, вызовы отрисовки, память) — из вывода ворот или ревизора, а не на глаз.
4. **Превышение бюджета — стоп-линия**, как красная сборка `android` (ТАБУ №0.01 п. 2): сначала уложиться в бюджет (сжать, выбросить, упростить, вынести из APK), потом новая работа. Бюджет повышается только с новым замером и строкой хора «предубеждение / контраргумент / почему» в `docs/APK_REQUIREMENTS.md`.
5. **Что не идёт в APK.** Всё, что по нормам размещения живёт на Webtypikon (текстовая версия, библиотека богослужебных книг), в APK не кладётся; если оператор решит иначе, ревизор сначала считает цену в мегабайтах и памяти.
6. **Честность.** Ревизор мерит сборку и сцену на компьютере; частоту кадров, нагрев и память в Quest 3 подтверждает только шлем и оператор (ТАБУ №0.02 п. 4). Число без команды или источника в ревью не пишется.
7. **Конституция:** ФОРМА (что шлем может нести: мегабайты, память, кадры) → ДЕЙСТВИЕ (каждая задача меряется и укладывается в бюджет до слияния) → ЦЕЛЬ (созерцание без рывков: заикание кадра ломает theoria, а лишнее в шлеме — не учит).

## 🛑 ТАБУ №0.012: РЕКВИЗИТ — РАННЕР БЕРЁТ ВСЁ, ДАЖЕ НЕ ИГРОВОЕ (оператор, 2026-09-30)

**Приоритет:** выше табу, ниже Конституции с правилом решений; меняет фильтры ТАБУ №0.1 (п. 3 «только игровые объекты») и ТАБУ №0.15 (п. 4 «не игровой объект — отказ»).

**Решение оператора (дословно):** «бери все даже не игровое нам в реквизит. это правило клауд мд выше и табу».

1. **Не игровое — не отказ, а реквизит.** Картинки из `examples/`, `docs/`, `tests/`, скриншоты, редакторы, промо и прочее, что раннер раньше отклонял как «не игровой объект», теперь берутся в реквизит обители. Каждая такая вещь записывается в реестр реквизита с репо, ревизией, путём, лицензией, видом (пример, скриншот, редактор, документ) и дефицитом, под который её нашли.
2. **Что остаётся под запретом.** Святыни из сырья и догматический стоп-лист не берутся и в реквизит (ТАБУ №0.2, №0.35 п. 5–6: святое не бывает производной чужого). Репо без лицензии — «все права защищены», из него не берётся ничего.
3. **В игру — только через раннер.** Реквизит — это склад. В сцену и в APK вещь из реквизита попадает только после конвейера ТАБУ №0.1: форма по альфе ≥ 35 %, 12 вариаций, мета-json, реестр лицензий, проверка глазами на контактном листе.
4. **Склад не раздувает APK и репо.** Реквизит лежит вне APK, пока его не взяла сцена; вес склада и прирост за проход меряет ревизор лимитов (ТАБУ №0.011).
5. **Журнал.** Каждый проход пишет, сколько взято в реквизит, по видам. Журнал не удаляется (ТАБУ №0.25 п. 5).
6. **Конституция:** ФОРМА (материал мира как он есть, с его правами) → ДЕЙСТВИЕ (взять всё на склад, а в игру — только переработанное под учительный слот) → ЦЕЛЬ (реквизит служит сцене, не подменяет её).

## 🛑 ТАБУ №0.013: ЭТАЛОН ЛОКАЦИИ — «КЕЛЬЯ ВЕЧЕРНЕГО ДОЗОРА С ПРЕДМЕТАМИ ОБИТЕЛИ» (оператор, 2026-09-30)

**Приоритет:** выше табу, ниже Конституции с правилом решений; действует вместе с ТАБУ №0.07 (отбор объектов), №0.011 (лимиты APK) и №0.012 (реквизит).

**Решение оператора (дословно):** «келья вечернего дозора с предметами обители хорошо получилась»; «задача для клауд мд правилом келья вечернего дозора с предметами обители табу и выше»; «99 локаций добавь по 299 нашим сюжетам. бери предметы из 99 репо которые склонировали».

**Эталон** — `godot/scripts/rule_cell.gd` + `godot/scripts/obitel_layout.gd` (слоты кельи) + `godot/tests/test_obitel.gd`; кадры `docs/audit/2026-09-30/godot-hub-evening-cell.png`, `godot-hub-evening-watch.png`. Каждая новая локация (в том числе 99 локаций по сюжетам) строится так же:

1. **Сердце места — одна практика или одно действие** с учительной целью, логика отдельно и под тестом (как `RuleCore` у дозора). Подсказка у сердца называет именно его: соседние вещи не перехватывают выбор.
2. **Стены и свет задают место.** Свой класс света по ТАБУ №0.38 (у дозора — глиняная лампа около 1900 K, рабочий свет, а не лампада); святыня получает лампаду только там, где ей место.
3. **Предметы — настоящие и отобранные.** Честный пул и пять критериев ТАБУ №0.07; предметы из 99 склонированных репо — через склад реквизита (ТАБУ №0.012) и конвейер ТАБУ №0.1 (35 %, 12 вариаций, проверка глазами), свои — через объёмные прокси ТАБУ №0.32. Предмет, не похожий на свою вещь, не ставится.
4. **Расстановка по слотам вокруг сердца:** на стене, на столе или скамье, на полу; сердце и проходы свободны; не больше двух состояний одной вещи; бирка видна только вблизи (3,2 м).
5. **Святыня — только на своём месте:** плоская доска или утварь с `noInteract`/`noLoot`, без бирки, без свечения и нимба; святое не ключ и не находка.
6. **Тест места:** раскладка детерминирована; каждый предмет не ближе 0,75 м к точке взаимодействия (так тест поймал коврик у аналоя и гончарный круг у журнала); модели ≤ 5000 треугольников; флаги святынь; ни одного церковного слова в бирках.
7. **Кадры глазами:** вид места и вид его панели; подсказка у сердца читается правильно; снимки — в `docs/audit/<дата>/`.
8. **Мера:** ревизор лимитов APK (ТАБУ №0.011) считает прирост каждой локации в мегабайтах, треугольниках и вызовах отрисовки до слияния.
9. **Конституция:** ФОРМА (место, его свет и его настоящие вещи) → ДЕЙСТВИЕ (одна практика в сердце места) → ЦЕЛЬ (вещи служат учению, а не заслоняют его).

### Работа раннера — дословно, шаг за шагом

Раннер — это GitHub Actions workflow `.github/workflows/raw-asset-intake.yml` (ручной запуск `workflow_dispatch`, `ubuntu-latest`). Шаги:

1. **Checkout ludus**, установка Python 3.12, `pip install pillow pycodestyle`.
2. **PEP 8-ворота:** `python -m pycodestyle scripts/raw_assets/`; при нарушении сборка падает.
3. **Приём сырья** (`scripts/raw_assets/intake.py`):
   - список репо берётся из `backlog` (все ссылки `https://github.com/owner/name` по порядку, без повторов), фильтр `--only`, лимит `--max-repos`;
   - каждое репо клонируется `git clone --depth 1 --filter=blob:none --no-checkout` и `git sparse-checkout set --no-cone '/*LICEN*' '/*COPYING*' '/*COPYRIGHT*' '*.png' '*.svg'`: скачиваются только изображения и тексты лицензий, исходники игры не тянутся;
   - лицензия определяется по верхнеуровневому файлу (AGPL, LGPL, GPL-3/2, MPL, CC-BY-SA, CC0, MIT, Apache); фиксируются ревизия (`git rev-parse HEAD`) и путь каждого файла;
   - игровые объекты (слова `sprite, item, tile, character, hero, monster, npc, unit, portrait, building, terrain, icon, object, prop, effect`) идут в конвейер; скриншоты, заставки, промо и прочее не игровое — в реквизит (ТАБУ №0.012); шрифты исключаются;
   - результат — `build/raw/manifest.json`.
4. **Переработка и замер** (`scripts/raw_assets/transform.py`):
   - спрайт-листы режутся на отдельные объекты рекурсивным XY-разрезом по прозрачным промежуткам; непрозрачный фон удаляется по цвету углового пикселя; альфа ≤ 16 считается пустотой;
   - каждый объект ставится на общий холст 256×256 (одинаковый для «до» и «после»);
   - **форма определяется только альфа-каналом** (правила 1–12 ниже); яркость на форму не влияет;
   - измеряются две величины: **изменение формы** = |A XOR B| / |A ∪ B| по альфа-маскам источника и результата, и **изменение цвета** в пределах площади объекта;
   - объект принимается, только если **обе** величины ≥ 35 %;
   - если объект не прошёл, он **замещается Антагонистом** (домен III): в православной игре антагонисты — **восемь страстей** (чревоугодие, блуд, сребролюбие, гнев, печаль, уныние, тщеславие, гордость);
   - для каждого базового объекта и антагониста генерируется **ровно 12 детерминированных вариаций** (домен IV) с seed = sha1(репо + путь + номер куска); каждая вариация замеряется отдельно, у всех 12 разные хитбоксы;
   - если фигура теряет свои тёмные непрозрачные пиксели, объект останавливается с ошибкой `Alpha_Silhouette_Error`;
   - результат — `build/derived/*.png` (RGBA, прозрачный фон), `ant_<страсть>_<id>_vNN.png`, мета-json на каждый спрайт и отклонённые пары в `build/derived/rejected/` для проверки глазами.
5. **Реестр и формула** (`scripts/raw_assets/register.py`): `THIRD_PARTY_NOTICES.md` (источник, ревизия, путь, лицензия, % цвета, % формы) и лист «Формула» на каждый объект (п. 1: «отличающийся тем, что…», п. 2: оба изменения ≥ 35 %).
6. **Контроль дельты** (`scripts/raw_assets/check_delta.py`): любой ассет в `public/ludus/art/derived/` без мета-json или с изменением формы < 35 % валит сборку с сообщением «Требуется Антагонист».
7. **Артефакт:** `build/derived`, `THIRD_PARTY_NOTICES.md` и `manifest.json` выгружаются артефактом на 14 дней. **Автокоммита нет:** человек подтверждает лицензию и отбирает объекты, затем они коммитятся в `public/ludus/art/derived/` вместе с мета-json.

**Код как сырьё.** Сторонний код тоже проходит раннер: `scripts/raw_assets/code_delta.py` сравнивает исходный модуль с нашей реализацией по нормализованным токенам (без комментариев и пробелов). Изменение считается как 1 − схожесть последовательностей токенов и должно быть ≥ 35 %. Переписывание на язык проекта (JS/TS/C#/Python) засчитывается, но **замеряется**. Результат тоже попадает в `THIRD_PARTY_NOTICES.md`.

## 🛑 ТАБУ №0.2: БОГОСЛОВИЕ И ДОГМАТЫ — ЗВУК, ОБРАЗ, МЕХАНИКА (2026-09-29)

1. **Святые — только православные.** Инославные святые после разделения 1054 г. в игре не выводятся. Замены по резолюции оператора (ТАБУ №0.25): Хильдегарда → прп. Кассия; Бонавентура → свт. Григорий Палама; Екатерина Сиенская → вмц. Екатерина Александрийская (освободившееся место — прп. Макрина Младшая).
2. **Игровой образ — не икона.** Нимб принадлежит иконе, поэтому в игровой графике святость показывается атрибутами (свет, свиток, орарь, вервица), а не нимбом. Источник: комментарии «§9.0 … без нимбов» в SVG проекта (obj-lampada.svg, npc-tabib.svg) и решение оператора 2026-09-29. В самом тексте §9.0 (webtypicon2 `docs/ru/АРТ_ПРОМПТЫ_КАРТЫ_И_КОСТИ_2026-08-17.md`) этой строки нет; её надо туда добавить.
3. **Антагонисты — страсти, а не святыни.** Противники — восемь страстей (помыслов) по прп. Иоанну Лествичнику и Евагрию. Святое (крест, имя Божие, молитва, икона, литургия) никогда не бывает врагом, добычей, оружием или множителем очков.
4. **Молитва не заклинание.** Иисусова молитва и священные имена сопровождают путь игрока, но не «усиливают» его. Страсть побеждается трезвением и безмолвием (исихией), а не «сакральным оружием».
5. **Богослужение а капелла.** Инструменты не имитируют церковное пение. Пение передаётся голосоподобным исоном; колокола звучат по уставу: благовест зовёт на молитву, трезвон — праздник и радость, перебор — скорбь. Колокол не используется как «дзинь за награду».
6. **Безмолвие — осмысленное состояние.** Тишина — это состояние звука со смыслом; апофатические врата звучат почти тишиной.
7. **Тексты на церковнославянском и греческом** не искажаются ради эффекта: они не режутся, не зеркалятся и не глитчатся.
8. **«Прелесть» как принцип дизайна.** Антагонист, который выглядит как награда (правило 33), — это богословски точный образ прелести. Он допустим, если игрок может его распознать по трезвению (подсказки в диалогах наставников).
9. **Спорные богословские решения** проходят хор (ТАБУ №0.5) с голосом «Богослов» и ссылкой на источник (Святое Писание, отцы Церкви, устав).

**Приоритет:** сразу после ТАБУ №0.25. Это единственное исключение, которое оператор сделал к правилу о журналах.

**Решение оператора (дословно):** «сделай с механизмом не сохранения логов пользователя для таинства исповеди и это декларируй». Уточнение: «Логи наоборот уничтожаются. Описка моя» — это относится **только к исповеди**; общее правило ТАБУ №0.25 п. 5 (журналы Ордена не уничтожаются) остаётся в силе. «Исповедь часто видел на сайтах. Игра не совершает таинство.» «Евхаристию — только в сюжете.»

**Декларация:** `docs/CONFESSION_PRIVACY_DECLARATION.md`.

1. **Игра таинство не совершает.** Разрешение даёт только священник в храме. В игре есть только подготовка — испытание совести, личный листок, который «сгорает». Листок прямо говорит: «Это не таинство».
2. **Ничего не хранится и не передаётся.**
   - Текст живёт только в поле ввода.
   - Нет localStorage, sessionStorage, IndexedDB, cookies, Cache API, service worker, fetch, XHR, beacon, WebSocket, Firebase, консоли, аналитики и журнала.
   - Не записывается даже факт открытия листка.
3. **Нет следа в игре:** счётчика, награды, атрибута, врат, ачивки. Исповедь — не 13-я практика и не механика (ТАБУ №0.35 п. 16, ТАБУ №0.4).
4. **Сжигание.** При «Сжечь листок», закрытии, Esc и уходе со страницы поле затирается и очищается, а окно удаляется. Проверка орфографии и автозаполнение выключены.
5. **Изоляция и проверка.**
   - Модуль `ludus-confession.js` ни от чего не зависит.
   - CI-тест `tests/ludus-confession.test.js` валит сборку, если в модуле появится API хранения, сети, логирования или событий.
   - Любая правка модуля проходит хор ТАБУ №0.37 и повторный прогон Playwright с меткой.
6. **Честная граница.** Сборщик мусора, своп ОС и сторонние клавиатуры неподвластны странице, это сказано в декларации. Для полного отсутствия следа листок советует писать на бумаге.
7. **Логи исповеди уничтожаются.**
   - Всё, что касается исповеди, уничтожается: листок сжигается, окно удаляется, служебных записей не создаётся.
   - Журналы Ордена (действия, раннер, OSINT, патентные листы) по ТАБУ №0.25 п. 5 по-прежнему не уничтожаются. Исповедь — единственное исключение.
8. **Евхаристия — только в сюжете.**
   - Литургия и Причащение присутствуют как событие жизни обители, которое игрок видит издали: братия идёт к чаше, звучит исон, горит лампада.
   - Интерактива, кнопки, листка подготовки, счётчика, награды и механики у Евхаристии нет.
   - Игрок не причащается в игре, и Святые Дары не изображаются как предмет.
   - Потир и дискос в инвентаре — только утварь с флагом `noLoot`, без действия «причастить».
   - CI-тест валит сборку, если среди практик или кнопок появится Причащение.
9. **Голосовой ввод: в шлеме запрет, на остальных устройствах предупреждение.** Решение ведущего по поручению оператора («разреши»).
   - На Quest, Pico и в Wolvic поля для записи нет: листок показывает только вопросы и советует бумагу или тишину сердца.
   - Причина: голосовой диктовкой системной клавиатуры управляет ОС, речь может уходить на серверы производителя, и страница выключить это не может. Предупреждение там было бы обещанием, которое код не держит.
   - На компьютере и телефоне поле есть, но с явным предупреждением: не диктовать голосом, не пользоваться сторонней клавиатурой.
   - Предубеждение: «запрет лишает игрока листка». Контраргумент: вопросы остаются, а запись без утечки в шлеме невозможна. Итог: честный запрет лучше невыполнимого обещания.
10. **Семь таинств в VR: игрок — свидетель.** Спецификация: `docs/SACRAMENTS_VR_SCENES.md`. Наборы сцен: `public/vr/models/scene/sacrament-*.glb` и `.json`.
    - Таинств семь (Катехизис свт. Филарета): Крещение, Миропомазание, Причащение, Покаяние, Священство, Брак, Елеосвящение. Число «12» у оператора — двунадесятые праздники, они прорабатываются отдельно.
    - Игра таинств не совершает. В каждой сцене игрок стоит у черты свидетеля: может подойти, стоять, склонить голову, уйти.
    - У святынь флаги `noInteract` и `noLoot`. Нет механики, награды, атрибута, врат и журнала присутствия.
    - Исповедальный угол: аналой с Крестом и Евангелием, лампада перед иконой, тишина, листок подготовки. Разрешительной молитвы в игре нет.
    - **Микрофон в зоне таинства выключен жёстко.** Событие `ludus:sacred-zone` в `vr.js` останавливает распознавание речи, прячет и блокирует кнопку до выхода из зоны. Запись голоса невозможна.

Пометка «[уточнено]» означает, что формулировка оператора исправлена ради Конституции, богословия или фактов проекта; причина указана в скобках.

3. «Победы» тонировки, при которых исчезают тёмные силуэты, признаются системной галлюцинацией.
4. При обработке листа сначала строится бинарная карта плотности (Solid/Empty) по прозрачности (альфа > 16 — Solid).
5. Автоматическое перекрашивание приравнивается к 0 % переработки.
6. Спрайт считается пустым, только если у всех пикселей A = 0 (после отсечения шума ≤ 16).
7. [уточнено] Алгоритмы, определяющие **форму** по порогу светимости, изолируются и удаляются. Светимость допустима только в метрике изменения цвета.

9. Алгоритм смотрит как акустическое зондирование термоклина: ищет плотность границы сред, а не её цвет.
10. Деформация изменяет массив непрозрачных пикселей, а не их RGB-векторы.
11. Знаки `#` и `$` обрабатываются как геометрические полигоны, а не как типографские символы.
12. Если спрайт теряет целостность силуэта в тёмных зонах, объект останавливается с ошибкой `Alpha_Silhouette_Error`.

**Домен II. Порог истинной мутации (≥ 35 %)**
13. Изменения на 3–12 % (огненные шары, глифы) — косметический шум; они отбраковываются.
14. Минимальный порог принятия редизайна — 35 % изменения топологии контура.
15. Дельта 35 % достигается структурной перестройкой (отростки, каверны, шипы), а не масштабированием.
16. Смещение внутренних пикселей без изменения внешней границы идёт с коэффициентом 0,1.
17. Устранение острых углов у `#`/`$` засчитывается, если меняет геометрию коллизий.
18. Оранжево-золотой градиент не даёт скидки на деформацию формы.
19. Любой анализ пары «источник → результат» содержит вычисленный процент изменения формы.
20. Если дельта < 35 %, результат уходит на протокол «Антагонист».
21. Контраргумент лени: «Цвет освежает картинку». Ответ: «Освежает фасад, структура остаётся прежней».
22. [уточнено] Дельта формы = |A XOR B| / |A ∪ B| по альфа-маскам (это то же, что 1 − IoU; нормировка на объединение, чтобы маленький объект не давал ложных 100 %).
23. Добавление хвоста кометы к шару легитимно увеличивает дельту.
24. Доказательство трансформации — наложение двух силуэтов (пара «источник → результат» в отчёте).

**Домен III. Протокол Антагониста**
25. Правило замещения: объект, не прошедший порог 35 %, заменяется Антагонистом.
26. [уточнено] Огненный шар → страсть **гнева** (раньше предлагались «вакуум или ледяной фрактал»; в православной игре противник — страсть, а визуальную инверсию даёт ледяная, комплементарная палитра).
27. [уточнено] Монеты (`$`) → страсть **сребролюбия** («паразиты и чёрные дыры» заменены страстью, образ паразита остаётся визуальным мотивом).

   - промт даёт примитив по полю `box`.
   В мета-json он помечен `"lod": "proxy"`. Полная модель получает `"lod": "final"` и заменяет прокси тем же id. Прокси не выдаётся за готовую модель (дайджест п. 1).
3. **Иконы остаются плоскими.** Икона в VR — доска-предмет: плоская панель в киоте или иконостасе с флагами `noInteract`/`noLoot`. Святые в образе статуй-скульптур не делаются, это чуждо православному образу (VII Вселенский собор: почитание образа). Святые как NPC — это люди-персонажи, без нимба (ТАБУ №0.2 п. 2). Крест, потир и колокол из сырья не моделируются (ТАБУ №0.35 п. 6).
4. **Коллизии по форме.** Коллайдер строится по силуэту (альфа) или по полю `box`, а не по светящемуся контуру (ТАБУ №0.3 п. 51, 76). Масштаб — метры, для Quest 3 соблюдается бюджет: прокси ≤ 5 000 треугольников, без внешних текстур.
5. **Инструмент.** Генератор `scripts/meta3d/`: three.js (MIT) SVGLoader + ExtrudeGeometry + GLTFExporter в Chromium. Закрытый Needle Engine для генерации не используется (ТАБУ №0.25 п. 4).
6. **Проверка.** CI считает покрытие: число `.glb` = число SVG + число промтов. Нехватка валит сборку с сообщением «Нет объёма для Meta».

## 🛑 ТАБУ №0.39: ЭЗОПОВ ЯЗЫК ГЕРОЕВ — СМЫСЛ КОНСТИТУЦИИ ЧЕРЕЗ МИРОВОЗЗРЕНИЕ КАЖДОГО (оператор, 2026-09-29)

**Приоритет:** выше ТАБУ №0.38 и №0.4; ниже Конституции и ТАБУ №0.1–0.35.

**Решение оператора (дословно):** «эзопов язык вводи везде в игре из-за этого, смысл конституции игры — через эзопов язык героев, у каждого свой, через мировоззрение».

**Почему.** Церковное слово в интерфейсе — «мученичество» в ачивке, «благодать» на кнопке — низводит святое до механики (ТАБУ №0.4). Поэтому ФОРМА → ДЕЙСТВИЕ → ЦЕЛЬ передаётся иносказанием: притчей, ремеслом, образом. Смысл узнаёт тот, кто видит, и никто не получает его как ярлык.

1. **У каждого героя свой язык по его мировоззрению и ремеслу.** Героем может быть NPC, наставник, страсть или протокол.
   - Рыбак говорит сетью, глубиной и уловом.
   - Гончар говорит глиной, кругом и обжигом.
   - Оператор ROV говорит термоклином, давлением и эхом.
   - Караванщик говорит дорогой, привалом и грузом.
   - Писец говорит чернилами, строкой и полем листа.
   - Кочевник говорит небом, конём и кочевьем.
   - Страсть говорит языком выгоды, протокол Кащея — канцеляритом цены.

   В `data/dialogue-trees.json` у каждого NPC есть поле `idiom`: словарь его образов и 3–5 опорных метафор. Реплика без образа своего ремесла не принимается.
2. **Иносказание передаёт смысл, а не прячет ложь.** Каждая эзопова реплика несёт поле `meaning` — прямой смысл для Богослова и патристический `source` (ТАБУ №0.35 п. 18). Смысл обязан совпасть с Конституцией и вероучением. Двусмысленность, которую можно прочитать как ересь, не допускается.
3. **Интерфейс говорит образами, а не церковными терминами.** В кнопках, ачивках, SKU и названиях механик нет слов «мученик», «святой», «благодать», «таинство», «спасение». Вместо «мученичества» — «он не отступил»; вместо «благодати» — «свет пришёл сам». Прямое слово Церкви звучит только из уст героя в живой речи, с источником, и никогда как ярлык награды.
4. **Святое иносказанием не пародируется.** Эзопов язык не касается текстов Писания и богослужения: церковнославянский и греческий не перефразируются в шутку, не режутся и не глитчатся (ТАБУ №0.2 п. 7). Герой может сказать о молитве притчей, но не переиначить её слова.
5. **Мировоззрение видно в том, как герой молчит.** Наставник-исихаст отвечает паузой и одним образом. Скоморох отвечает прибауткой. Протокол Кащея отвечает цифрой. Страсть отвечает посулом, и у посула всегда есть признак распознавания (ТАБУ №0.2 п. 8).
6. **Одинаково в обеих версиях.** Meta (голос, образ, звук) и текстовая версия на Webtypikon (только текст) пользуются одними и теми же `idiom` и `meaning`.
7. **Проверка.**
   - CI-схема диалогов валит сборку, если у реплики нет `meaning` или `source` или если у NPC нет `idiom`.
   - Стоп-лист церковных терминов проверяет строки UI (`data-i18n`, ачивки, SKU).

5. У каждой подделки святого (Технославие, купола-обтекатели, облачные «предки», Ирий, «иконы-баффы») есть признак распознавания: цена, счётчик, мигание, петля, отсутствие тишины. Хотя бы одна реплика наставника учит этот признак (прелесть, ТАБУ №0.2 п. 8).

7. Мученик — свидетель. Жертва героя сохраняет имя, память и лицо. Слова «мученик», «святой», «благодать», «таинство» не используются в UI, ачивках, SKU и названиях механик.

10. Визуал и звук — прибор расследования: реакция на близость узла (200/50/10 м), тройка «звук, свет, хаптика» в одном кадре, детерминированный seed.
11. Искажённое горловое пение — голос меша. Живое тувинское и алтайское горловое пение — человеческая традиция, а не маркер «заразы».

## 🛑 ТАБУ №0.5: CHORUS DECISION FRAMEWORK — АРИСТОТЕЛЕВА ДИАЛЕКТИКА

**Дата внедрения:** 2026-09-29  
**Приоритет:** ВЫШЕ, чем локальные оптимизации  
**Применение:** Все критические решения на фазах разработки

### Принцип: Множественные Голоса, Одно Решение

Когда стоит выбор между вариантами реализации (выбор из 24 вариантов из 999 по 32 параметрам проекта):

**ШАГ 1 — Слушать хор (Chorus Auditio):**
- Perspective A (Инженер): "Как реализовать технически оптимально?"
- Perspective B (Тестировщик): "Как это протестировать без слепых зон?"
- Perspective C (Пользователь): "Что это значит для игрока/учебного опыта?"
- Perspective D (Архитектор): "Как это встраивается в систему Demiurgic Causality?"

**ШАГ 2 — Найти один вариант (Dialectical Synthesis):**
- Вариант правильный не потому, что все согласны, а потому что:
  1. Соответствует Constitution (Demiurgic Causality)
  2. Тестируется полностью
  3. Работает для игрока
  4. Масштабируется (32 параметра проекта учтены)

**ШАГ 3 — Документировать решение (Why, not What):**
- Запиши NOT: "Сделали X"
- Запиши: "Выбрали X потому что A+B+C+D согласились что..."
- Это правило раз в час критических решений

### Принципы реализации

#### 1. Диалоги NPC (Разговоры в аппарате)

- **Каждый диалог учит** — не просто рассказывает, а передаёт знание через диалектику (Sokratic method)
- **Ветвление по ФОРМЕ** — разные ответы для Wisdom ≥ 8 vs < 5; Faith влияет на доступные пути
- **NPC имеют позицию** — Elder Sergius следует Hesychasm, Theodora проповедует практику, каждый учит своим путём
- **Память** — NPCs помнят выбор игрока, повторяющиеся встречи углубляют отношение (progression)

#### 2. Звуки (Хором гуру — смачно и красиво)

- **Звук отражает ФОРМУ** — высокие ноты для духовного подъёма (Wisdom), низкие для укоренения (Constitution)
- **Музыка учит** — православная литургия, паузы для размышления, хоральные полосы как голос монастыря
- **Никакого "чистого" дизайна** — каждый SFX имеет смысл (звон колокола = молитва передана, шум ветра = изменение миров)
- **Пространственный звук** — NPC голос идёт из их позиции в сцене, молитва окружает игрока в 3D

#### 3. Система атрибутов

**7 атрибутов, каждый отражает аспект духовного роста:**

| Атрибут | Значение | Источник (Patristic) | Диалоговое влияние |
|---------|----------|----------------------|-------------------|
| **Wisdom** | Понимание учений, Noesis | Gregory of Nyssa | Доступ к глубоким диалогам, разгадка тайн |
| **Faith** | Вера, πίστις | Pseudo-Dionysius | Одобрение от духовных NPC, чудеса |
| **Dexterity** | Ловкость действия, практика | John of Damascus | Успех в ритуалах, быстрые решения |
| **Constitution** | Выносливость, постоянство | Isaac the Syrian | Пост, долгие молитвы, сопротивление |
| **Charisma** | Влияние, лидерство | Gregory the Theologian | Убеждение, создание общины |
| **Cunning** | Хитрость, стратегия | (Редко, не одобряется) | Тайные пути, исключения |
| **Erudition** | Знание текстов | Synaxarion tradition | Разблокировка knowledge gates |

**Источник и использование:**
- Диалоги с NPCs дают +1 до +5 к атрибутам (зависит от глубины выбора)
- Knowledge gates требуют порога (Wisdom ≥ 7 для access to Apophatic Theology)
- Никаких случайных бросков — только выбор и его следствия

#### 4. Knowledge Gates (Ворота знания)

Система **Gating** проводит игрока через 6 уровней духовного роста:

```
1. Foundational (основание) — Евангелие, азы веры
2. Liturgical (литургическое) — Служба, молитва в общине
3. Ascetic (аскетическое) — Пост, монашеская дисциплина
4. Contemplative (созерцательное) — Noesis, молитва сердца
5. Mystical (мистическое) — Theoria, видение Бога
6. Apophatic (апофатическое) — Отрицательная теология, молчание
```

Каждый уровень требует:
- Определённых атрибутов (Wisdom ≥ 4, 6, 8, 10, 12, 14+)
- Диалогов с конкретными NPCs
- Выполнения ритуального действия (молитва, пост, медитация)

#### 5. Firestore как "Небеса" (Database Shape)

Структура должна отражать теологию:

```
ludus/
├── players/{playerId}
│   ├── form: { wisdom, faith, dexterity, … }
│   ├── actions: { prayerCount, fastDays, meditationHours }
│   └── goal: { currentGate, enlightenmentLevel, npcRelations }
├── npcs/{npcId}
│   ├── name, theology, role
│   ├── dialogueTree: { nodes, branches }
│   └── memory: { playersInteracted, depth }
├── knowledgeGates/{gateId}
│   ├── level, requirements, theologicalTheme
│   └── testNode: { question, attributes_required }
└── telemetry/{rovId}
    ├── depth, temperature, pressure
    └── playerInsight: { attribute, bonus }
```

## Практические следствия для разработки

### A. Диалоги (NPC_DIALOGUE_SYSTEM.md)

✅ **Требуется:**
- Каждый NPC имеет полное диалоговое дерево (≥ 5 узлов)
- Ветвления по ФОРМЕ (Wisdom, Faith, Dexterity checks)
- Бонусы атрибутов за правильные ответы
- Память (NPC помнит прошлые встречи)
- Соответствие паtristic источникам (Gregory of Nyssa, Isaac the Syrian и т.д.)

❌ **Запрещено:**
- Бессмысленные диалоги ("Привет!" без учения)
- Случайные бонусы (только выбор → следствие)
- NPC без позиции (все обязаны иметь теологическую позицию)

### B. Звуки (SOUND_DESIGN_SYSTEM.md)

✅ **Требуется:**
- Минимум 40 музыкальных треков (12 ambient + 8 NPC theme + 6 gates + 9 attributes + 5 story moments)
- 12 хоровых произведений (32-голосный SATB)
- Динамическое смешивание (музыка → диалог → SFX → амбиенс)
- Пространственный звук (биинауральная обработка для Quest 3)
- Каждый звук имеет **смысл** (не просто красиво, а учит)

❌ **Запрещено:**
- EDM, синтезаторные звуки без смысла
- Фоновая музыка "для затычки"
- Звуки без связи с игровым состоянием

### C. ROV Lake (Интеграция)

✅ **Требуется:**
- ROV telemetry → Firestore → Атрибуты игрока
- Глубина (depth) → Wisdom бонус за наблюдение
- Температура (temp) → Уроки о разных средах
- Джойстик интеграция с диалогом (рука + молитва одновременно)

### D. Фронтенд (webtypicon2 ludus-game.js)

✅ **Требуется:**
- NPC появляется в сцене → диалоговое дерево загружается
- Выбор варианта → проверка ФОРМЫ → отправка в Cloud Functions → получение ответа + бонусов
- UI показывает текущие атрибуты + бонусы за диалог
- Offline sync (диалоги работают offline, sync при reconnect)
