
**Миграции.** `ProfileStore.migrate()` выполняет merge-поверх-дефолтов и
глубокий merge известных вложенных таблиц. Добавление нового поля
безопасно для существующих профилей.

**Проекция на клиент.** Клиент никогда не видит raw-профиль. Он получает
`Types.ClientState` — явную проекцию без `sessionLock`, без `relics`,
без `history`. Это снижает и поверхность читерства, и размер пакета.

## 5. СЕРВЕРНАЯ АРХИТЕКТУРА И БЕЗОПАСНОСТЬ

### 5.1 Session Lock (DataStoreService)
- Загрузка через `UpdateAsync`: трансформация возвращает `nil`, если ключ
  уже залочен живой сессией (другой `jobId`, возраст < `LockStaleSeconds`).
- Просроченные локи (>120 с) считаются «мёртвыми» и перезахватываются —
  защита от краша сервера.
- `releaseAsync()` пишет финальное состояние и снимает лоск одним апдейтом.
- Autosave: каждые 90 с, каждая запись в отдельном потоке.

### 5.2 Асинхронное PvP (MemoryStoreService)
- **Ladder** — `SortedMap`, ключ = `userId`, sortKey = `pvpRating`,
  значение = `AttackSnapshot` (TTL 3600 с).
- **Pending** — `HashMap`, ключ = `userId`, значение = очередь
  последних 20 результатов, применённых при следующем входе.
- Матч **детерминирован**: сид = f(attackerUserId, defenderUserId,
  обе рейтинга). Это делает результат воспроизводимым для антифрода.

### 5.3 RemoteEvent / RemoteFunction Hardening
| Уровень | Механизм |
|---|---|
| Реестр | `Net.luau` — единственное место создания ремоутов |
| Rate-limit | `Guard.consume(player, key, N/мин)` — ведро на игрока |
| Типизация | `Guard.expectInt`, `Guard.isStringId` — падение на протоколе |
| Авторизация | все мутации только через сервисы; клиент шлёт «намерение» |
| Минимизация | ответ = `ClientState`, никогда не raw-профиль |

**Потолки:** `MaxRollsPerMinute = 20`, `MaxReportsPerMinute = 30`,
`MaxPvpPerMinute = 10`. Значения — в `Config.Limits`.

## 6. ТЕЛЕМЕТРИЯ ЭКОНОМИКИ (Faucets / Sinks)

| Faucet | Источник | Ставка |
|---|---|---|
| Денiers | `report:<region>` | 3 + 0.02·Σpower + rand(0,2) |
| Денiers | `submit_bonus` | 15% от суммы сданного |
| Денiers | `duplicate:<relic>` | 5 / 12 / 30 / 90 / 250 |
| Денiers | `pvp_spoils` | 5% power защитника |
| Лавры | `submit_laurels` | 1 за 5 отчётов |

| Sink | Цель | Ставка |
|---|---|---|
| Денiers | `fate_roll ×1` | 25 |
| Денiers | `fate_roll ×10` | 225 |

Наблюдаемость: `EconomyService.recent(userId, n)` — кольцевой буфер
последних 500 транзакций. Это **сигнал**, не durable-журнал. Durable
аналитика — предмет Фазы 4.

## 7. ДОРОЖНАЯ КАРТА ФАЗ 2–4 (заделы в коде)

**Фаза 2 — Монетизация.** Валюты `aspri` уже существуют в `Wallet` и
обрабатываются `EconomyService`. Точки интеграции:
`MarketplaceService.ProcessReceipt` → `EconomyService.credit(.., aspri, ..)`.
Time-skips = мгновенная регенерация энергии (без изменения `Config`).
Страховка «Пайцза» = флаг `seasonal["paiza_until"]`, читаемый в `AsyncPvp`
перед вычетом рейтинга. VIP «Патриарх» = множитель в `ReportService`
(сейчас 1.0 по умолчанию, множителя нет намеренно).

**Фаза 3 — Серверная архитектура.** Реализовано в Фазе 1; дальнейшее —
шардирование ладдера по сезонам и вынос `history` в отдельное хранилище.

**Фаза 4 — LiveOps (366 миссий).** Точки: `Types.Profile.seasonal`
уже персистится; `EconomyService` уже эмитит ledger-события; поле
`stats.season` в `Stats`. Требуется: сервис `LiveOpsService`,
конфиг `Missions[1..366]`, и подписчик на ledger для авто-прогресса.

## 8. МЕТРИКИ УСПЕХА ИТЕРАЦИИ

1. **D1 retention** ≥ 35% (ставка на 15-минутный цикл).
2. **Сессий/день на игрока** ≥ 2.0 (эффект «сумка отчётов переполнена»).
3. **Доля игроков, сделавших ≥1 PvP к дню 3** ≥ 25% (проверяет, что
   асинхронность работает без онлайн-пика).
4. **ARPPU Фазы 2** — цель будет установлена после сбора Day-7 данных.
5. **Faucet/Sink ratio** по денiers держать в диапазоне 0.85–1.10.
