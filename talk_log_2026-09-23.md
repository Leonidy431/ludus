# Talk log — 2026-09-23

## Entry: Phase 2 — 6DOF Underwater Physics & Buoyancy Engine

### Constraints applied
- CONSTITUTION.md isolation honoured: this is pure game code under
  `UnityVR/`; nothing references Webtypicon2 or any liturgical module.
- Additive only. No Phase 1 file (`IPlayerInput`, `InputProvider`,
  `MouseSimulatorInput`, `OpenXRInput`) is modified. Phase 2 lives entirely
  in the new `Assets/Scripts/Physics/` folder.
- Reference repo (`reference_repo/`) was not touched.

### Architectural reasoning
1. **Decoupling by struct + interface.** Physics must not know about devices.
   `VehicleCommand` is a pure struct and `IVehicleCommandSource` is the only
   seam the solver sees. `InputCommandAdapter` (the single Phase 1 → Phase 2
   bridge) turns `IPlayerInput` into `VehicleCommand`, so the same solver runs
   under the mouse simulator, OpenXR, an autopilot or a replay driver.
2. **Thermocline as a first-class system.** Instead of a single global density
   scalar, `WaterColumn` samples density *per volume at that volume's depth*.
   A hull straddling the thermocline therefore gets a correct pitch moment,
   which is the whole point of modelling stratification rather than faking it.
3. **Buoyancy via real Archimedes.** Per-volume spherical-cap submersion plus
   `rho·g·V` sums to force and `r × F` torque. No hand-tuned "stability"
   quaternions: righting moments emerge from geometry and mass distribution.
4. **Ballast as a first-order slew.** `ballastCommand` pumps
   `MoveTowards` at `ballastRatePerSecond` so diving/surfacing has a felt
   response time that the (future) dive computer can display.
5. **Water feel needs inertia.** Linear/quadratic drag alone feels like honey
   on rails; added mass (fraction of Rigidbody mass / inertia tensor) restores
   the "heavy but not mushy" quality expected of an underwater vehicle.
6. **Thrusters kept linear.** A per-axis allocation weight table keeps the hot
   path allocation-free and mixer-free. Normalising weights at author time is
   documented in HLD 4.5; a saturation solver can be added later if needed.
7. **XR2 budget.** FixedUpdate only, no LINQ, no closures, structs by value,
   trig confined to the submersion fraction. Documented practical caps of
   ≤ 12 volumes and ≤ 8 thrusters.

### Dependencies / assumptions
- `InputCommandAdapter` reads `MoveAxis`, `LookAxis`, `PrimaryTrigger` and
  `PrimaryGrip` from `IPlayerInput` exactly as declared in the Phase 1 contract
  table (HLD 3.1). If any of those members are named differently on the
  interface, only this one file needs adjusting.
- Binding fallback order: serialized `inputBehaviour` → self → children →
  idle. `SixDofBody.Bind(...)` and `InputCommandAdapter.Bind(...)` are provided
  for tests, autopilots and cutscenes.

### Deferred to later phases
- Cockpit lever/button eventing (Phase 3) will consume `SixDofBody` telemetry
  (`SubmergedFraction`, `DensityKgPerCubicMeter`, `BallastFill`, `DepthMeters`).
- CI/CD (Phase 4) will add the Android `.apk` build and a headless test run
  that exercises `WaterColumn` / `SixDofBody.SphereSubmergedFraction`.

## Entry: Phase 3 — Interactive Cockpit (Event System)

### Constraints applied
- CONSTITUTION.md isolation honoured: nothing under `UnityVR/` references
  Webtypicon2 or any liturgical module.
- Additive only. Phase 1 (`Assets/Scripts/Input/`) and Phase 2
  (`Assets/Scripts/Physics/`) are untouched. Phase 3 lands in a brand-new
  `Assets/Scripts/Cockpit/` folder.
- `reference_repo/` was not touched.

### Inputs read from the chat (Phase 1 contract is now locked)
`IPlayerInput` confirms the following members are the only surface Phase 3 is
allowed to touch: `HeadPose`, `IsPrimaryHandTracked`, `PrimaryHandPose`,
`MoveAxis`, `LookAxis`, `PrimaryTrigger`, `PrimaryGrip`, and the three
discrete events `PrimaryButtonPressed`, `PrimaryButtonReleased`,
`SecondaryButtonPressed`. `InputProvider.Current` is a static accessor and
`InputProvider.BackendChanged` fires when the active backend swaps. Phase 3
therefore subscribes to the *instance* events (never the static ones) and
pulls `InputProvider.Current` only as a last-resort fallback.

### Architectural reasoning
1. **Events, not references.** HUDs, audio, haptics and mission scripting must
   react to cockpit interactions without holding a reference to a specific
   lever. `CockpitEventBus` is a tiny multicast pub/sub with an `in`-free,
   allocation-free dispatch. Every control emits a `CockpitEvent` value
   (type + control + id + analog value + discrete state + world position +
   time). No listener is required for the game to work.
2. **One bridge to the input layer.** `CockpitInteractor` is the *only* file
   in the cockpit folder that implements `IPlayerInput`. It owns the hand ray,
   the hover bookkeeping, the grab threshold and the discrete-button routing.
   Controls see a `CockpitInteractionContext` value (input, hand position, ray,
   hit point, delta time) and nothing else, so they are device-agnostic and
   trivially unit-testable with a stub context.
3. **Freeze hover while grabbed.** If hover kept updating during a drag, a
   lever under the player's hand would flicker to whatever the ray passes over
   mid-swing. The interactor therefore stops calling `Physics.Raycast` for the
   duration of the grab and freezes `_hovered` to `_grabbed`. This is why the
   interaction is deterministic and cheap.
4. **Queued discrete presses.** `PrimaryButtonPressed`/`Released` are raised by
   the input backend, potentially mid-frame. The interactor never forwards
   them directly; it sets pending booleans and dispatches them at a stable
   point inside `Update`, after hover has resolved. That guarantees controls
   never see a press for a control that was not the current hover target.
5. **Analog maths shared between lever and dial.** Both rotate around a local
   hinge axis and derive their state from the signed angle between a captured
   reference direction and the hand's projection onto the plane orthogonal to
   the axis. `_referenceWorldDir` is captured at `GrabBegin` and held fixed
   for the drag, which means the identity "hand delta = control delta" holds
   even if the lever pose itself changes mid-grab.
6. **Hinge axis is invariant under its own rotation.** Because a rotation
   about an axis leaves that axis in world space invariant, `_hingeWorldAxis`
   (captured at `GrabBegin`) stays valid for the whole drag and does not need
   to be re-derived per tick.
7. **Base class owns identity, hover, highlight and emission.**
   `CockpitControl` is an abstract `MonoBehaviour` that registers itself with
   `CockpitManager` in `Awake`, unregisters in `OnDestroy`, tracks hover/grab
   booleans, paints an optional `Renderer` through `MaterialPropertyBlock`
   (no material instantiation), and exposes a single `Emit(...)` helper.
   Concrete controls (lever/button/toggle/dial) override only the callbacks
   they care about.
8. **Return-to-rest semantics.**
   - Lever: `springReturn` (momentary, e.g. rudder trim) vs. held position
     (e.g. throttle). `restValue` is authored as a normalised value.
   - Button: `_targetPress` is set by `ButtonDown/Up` but the visual plunger is
     animated by `MoveTowards` so the press reads mechanically rather than
     snapping.
   - Toggle: latches; the visual lever animates between `offAngleDeg` and
     `onAngleDeg` at `animateDegreesPerSecond`. The switch is assumed to be
     authored in its neutral (0°) pose; `Awake` offsets it to the starting
     state.
9. **Command source is deliberately narrow.** `CockpitCommandSource`
   implements Phase 2's `IVehicleCommandSource` and rebuilds a
   `VehicleCommand` from a designer-authored table of `ControlId` → axis
   bindings. It knows only about `CockpitLever` and `CockpitDial` for analog
   inputs, and about `CockpitToggle` for latching offsets. Buttons and
   general events are *not* routed into the command — they are for the HUD,
   mission script, and audio. This keeps control→thrust mapping in data, not
   in the solver.
10. **XR2 budget.** No LINQ, no closures, no per-frame `GetComponents*`
    (control lookup goes through a linear scan over ≤ 64 controls), no
    per-event allocation (`CockpitEvent` is a value struct; the bus holds one
    multicast delegate). `Physics.Raycast` is only issued when nothing is
    currently grabbed.

### Dependencies / assumptions
- Phase 3 depends only on `DeaconsPath.VR.Input` (for `IPlayerInput`) and
  `DeaconsPath.VR.Physics` (for `VehicleCommand` / `IVehicleCommandSource`).
  It never touches the Phase 1 or Phase 2 files themselves.
- `CockpitManager` uses `DefaultExecutionOrder(-95)`, which runs *after*
  `InputProvider(-100)` and *before* every control and the interactor
  (`-80`) / command source (`-70`). Registration therefore always succeeds
  before any other system queries the registry.
- `PersistAcrossScenes` on `CockpitManager` is off by default; each scene owns
  its own bus. This is intentional: a bus that leaks across a scene change is
  a classic source of dangling-subscriber bugs.

### Deferred to Phase 4 (CI/CD)
- Headless EditMode tests for `WaterColumn`, `SixDofBody.SphereSubmergedFraction`
  and the lever/dial angle maths.
- Android `.apk` build + IL2CPP verification on the Quest 3 profile.
