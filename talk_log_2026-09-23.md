## Entry: Phase 2 — 6DOF Underwater Physics & Buoyancy Engine

### Constraints applied
- CONSTITUTION.md isolation honoured: this is pure game code under
  `UnityVR/`; nothing references Webtypicon2 or any liturgical module.
- Additive only. No Phase 1 file (`IPlayerInput`, `InputProvider`,
  `MouseSimulatorInput`, `OpenXRInput`) is modified. Phase 2 lives entirely
  in the new `Assets/Scripts/Physics/` folder.
- Reference repo (`reference_repo/`) was not touched. The Freeciv reference
  insight provided no reusable drop-in code for a real-time VR solver, so
  nothing was ported from it; the module was authored from the HLD +
  constitution alone.

### Files landed
- `Physics/VehicleCommand.cs`          — pure pilot-intent struct.
- `Physics/IVehicleCommandSource.cs`   — the one seam the solver sees.
- `Physics/WaterColumn.cs`             — layered water + thermocline sampler.
- `Physics/BuoyancyVolume.cs`          — one displaceable spherical lobe.
- `Physics/ThrusterSpec.cs`            — one nozzle spec + per-axis weights.
- `Physics/SixDofBody.cs`              — the solver itself.
- `Physics/InputCommandAdapter.cs`     — Phase 1 → Phase 2 bridge.

### Architectural reasoning
1. **Decoupling by struct + interface.** Physics must not know about devices.
   `VehicleCommand` is a pure struct and `IVehicleCommandSource` is the only
   seam the solver sees. `InputCommandAdapter` (the single Phase 1 → Phase 2
   bridge) turns `IPlayerInput` into `VehicleCommand`, so the same solver runs
   under the mouse simulator, OpenXR, an autopilot or a replay driver.
2. **Thermocline as a first-class system.** Instead of a single global density
   scalar, `WaterColumn` samples density *per volume at that volume's depth*.
   A hull straddling the thermocline therefore gets a correct pitch moment,
   which is the whole point of modelling stratification rather than faking it.
   Two modes coexist: a two-layer smoothstep (default, cheap) and an authored
   ramp (arbitrary profile, still `O(ramp.Length)` and allocation-free).
3. **Buoyancy via real Archimedes.** Per-volume spherical-cap submersion plus
   `rho·g·V` sums to force and `r × F` torque. No hand-tuned "stability"
   quaternions: righting moments emerge from geometry and mass distribution.
   The exact cap formula `h²(3r − h) / 4r³` is used rather than a polygon
   approximation, and it is the *only* transcendental-ish hot path (one
   smoothstep in `WaterColumn`, no trig at all in `SixDofBody`).
4. **Ballast as a first-order slew.** `ballastCommand` pumps
   `MoveTowards` at `ballastRatePerSecond / ballastCapacityLiters` per second
   so diving/surfacing has a felt response time that the (future) dive
   computer can display. Ballast is added as extra dry mass with no extra
   displacement (tanks live inside the hull), matching real trim-tank
   behaviour: you get heavier, not bigger.
5. **Water feel needs inertia.** Linear/quadratic drag alone feels like honey
   on rails; added mass (a fraction of `Rigidbody.mass`, scaled by the
   submerged fraction) restores the "heavy but not mushy" quality expected of
   an underwater vehicle. It is computed from last-frame velocity rather than
   a solver-predicted acceleration, so it stays a single `AddForce` and no
   state machine is required.
6. **Thrusters kept linear.** A per-axis allocation weight table keeps the hot
   path allocation-free and mixer-free. Normalising weights at author time is
   documented in HLD 4.5; a saturation solver can be added later if needed.
   Default "six-pack" is generated in `Awake` so a bare GameObject is drivable
   without the user having to author seven nozzles first.
7. **Gravity ownership is explicit.** `Rigidbody.useGravity` is disabled in
   `Awake` and the solver owns both gravity (dry mass + ballast) and buoyancy
   in the same pass. This avoids the classic double-gravity bug when a hull
   straddles the surface.
8. **XR2 budget.** FixedUpdate only, no LINQ, no closures, structs by value,
   `GetComponents*` only in `Awake` (never per frame), trig confined to the
   submersion fraction. Documented practical caps of ≤ 12 volumes and ≤ 8
   thrusters.

### Dependencies / assumptions
- `InputCommandAdapter` reads `MoveAxis`, `LookAxis`, `PrimaryTrigger` and
  `PrimaryGrip` from `IPlayerInput` exactly as declared in the Phase 1 contract
  (HLD 3.1 and the `IPlayerInput.cs` source confirmed in chat). If any of those
  members are renamed, only this one file needs adjusting.
- Binding fallback order: serialized `inputBehaviour` /
  `commandSourceBehaviour` → self → parents → children → idle.
  `SixDofBody.Bind(...)` and `InputCommandAdapter.Bind(...)` are provided for
  tests, autopilots and cutscenes.
- `InputCommandAdapter` uses `DefaultExecutionOrder(-65)`, which runs after
  `InputProvider(-100)` and before `SixDofBody(-60)`, so the solver always
  reads a fresh command within the same FixedUpdate tick.

### Telemetry exposed for Phase 3
`SixDofBody` exposes `SubmergedFraction`, `DensityKgPerCubicMeter`,
`BallastFill`, `DepthMeters` and `IsSubmerged` as read-only properties so the
cockpit HUD and dive computer can consume them without reaching into the
solver. No event bus is added here — Phase 3 already owns `CockpitEventBus`,
and publishing from physics would create an unwanted Cockpit → Physics
dependency.

### Deferred to later phases
- Inverse thruster allocation / saturation solver (only if a vehicle is ever
  over-actuated).
- CI/CD (Phase 4) will add the Android `.apk` build and a headless EditMode
  test run that exercises `WaterColumn.DensityAt` and
  `SixDofBody.SphereSubmergedFraction` (both are `static`/pure and therefore
  trivially testable without a scene).
- Sonar / thermal visualisation of the thermocline (art pass, not physics).

## Entry: Phase 2 (completion) — Thruster Control Allocation

### Constraints applied
- CONSTITUTION.md isolation honoured: pure game code under
  `UnityVR/Assets/Scripts/Physics/`; nothing references Webtypicon2 or any
  liturgical module.
- Additive only. `SixDofBody`, `WaterColumn`, `VehicleCommand`,
  `IVehicleCommandSource`, `BuoyancyVolume`, `ThrusterSpec` and
  `InputCommandAdapter` are NOT modified. The new files stand beside them and
  can be adopted whenever a specific vehicle turns out to be over-actuated.
  The shipped Phase 2 mixer remains the default and is unaffected.
- `reference_repo/` was not touched.
- The Freeciv insight again only supplied process / DCC-badge context; no
  code was ported.

### Files landed
- `Physics/ThrusterAllocator.cs`  — ridge-regularised pseudo-inverse allocator
  with iterative saturation redistribution.
- `Physics/CommandWrenchMap.cs`   — pilot-channel → desired-wrench mapping
  that feeds the allocator.

### Architectural reasoning
1. **Why a separate allocator at all.** The Phase 2 mixer is deliberately
   forward-only: each nozzle's per-axis weight table is multiplied by the
   command and the resulting force/torque is applied directly. That works
   when the nozzle count is at most six and geometry is orthogonal, but
   N > 6 (over-actuation) makes the weight table ambiguous — some thrusters
   push against each other and total authority silently degrades. HLD 4.5
   already flagged this as deferred; this module closes that item without
   touching the linear mixer.
2. **Ridge-regularised least squares, not just a matrix inverse.**
   `u = argmin ||Bu − w||² + λ||u||²` is chosen over a raw pseudo-inverse
   because `BᵀB` is rank-deficient whenever N > 6, or whenever two nozzles
   advertise a nearly-identical wrench column (common when a ship authors
   port/starboard pairs). The `λ` term (default 1e-4) makes the system
   strictly positive-definite so Cholesky factorisation always succeeds and
   the allocator stays deterministic — a prerequisite for the anti-fraud
   replay the Roblox side already uses, since the VR build will eventually
   share seeds.
3. **Iterative saturation redistribution, not flat clipping.** Clipping
   alone would leave the requested wrench unmet and would also fail to
   rebalance onto the remaining free nozzles. Each pass finds the single
   worst violator, pins it at ±1, subtracts its contribution from the target
   wrench, and re-solves for the free set. This is the classic active-set
   allocator; it terminates in at most N passes and is exact whenever the
   wrench is achievable by any saturating assignment. `LastSolveSaturated`,
   `LastSaturationPasses` and `LastResidualSquared` are exposed so the
   cockpit dive computer can show "authority exceeded" warnings later without
   the physics module taking on a Cockpit dependency.
4. **Saturated nozzles are pinned, not zeroed.** A subtle bug that is easy to
   miss: after committing a clamp, the subsequent least-squares solve must
   not overwrite that value back to zero. `SolveActive` therefore writes an
   identity row with `_btw[i] = _u[i]` for inactive nozzles, which makes the
   Cholesky round-trip return the saturated value unchanged. This keeps the
   two solves in the same numeric domain (one matrix, one factorisation
   routine, one solve routine) rather than requiring two separate solvers.
5. **Sign convention deliberately matches SixDofBody.** The legacy mixer
   uses `linear = (Strafe, -Heave, Throttle)` and
   `angular = (Roll, Yaw, -Pitch)`. `CommandWrenchMap` uses exactly the same
   mapping so the allocator can be dropped in as a replacement without
   retuning every nozzle and every lever. Reversal authority is asymmetric:
   the map exposes `maxReverseForce` separately so a vessel can author a
   weaker astern force than its ahead force, which is realistic for a
   single-shaft propulsor and important for the ROV feel of the
   `oculus-knights` submersible.
6. **Data-in, data-out — no scene graph.** `ThrusterAllocator` never
   references a `MonoBehaviour`, `Rigidbody` or `Transform`. It is a pure
   numeric utility: `Configure(ThrusterSpec[])` at author time,
   `Allocate(force, torque, output)` per tick. `Configure` therefore also
   needs no `Awake` and can be exercised from an EditMode test with a
   hand-built `ThrusterSpec[]`, which is exactly what the Phase 4 CI
   harness will exercise alongside the existing pure statics.
7. **Local-frame wrench, caller rotates.** The allocator solves in the
   body's local frame, matching the frame in which `ThrusterSpec` data is
   authored. World-space rotation stays the caller's responsibility, which
   keeps the allocator free of scene state and lets the future
   `SixDofBody` integration call `AddRelativeForce` / `AddRelativeTorque`
   directly.
8. **XR2 budget.** Every scratch buffer (`_b`, `_btb`, `_btw`, `_u`, `_y`,
   `_l`, `_w`, `_w0`, `_active`) is allocated once in the constructor at the
   documented cap `MaxThrusters = 16`. `Configure` only writes into them;
   `Allocate` never allocates. Cholesky is `O(N³/6)` per saturation pass
   with a hard cap of `MaxThrusters` passes — for the default seven-nozzle
   six-pack that is well under a microsecond per FixedUpdate on the
   Snapdragon XR2. No LINQ, no closures, no `foreach` over reference types.

### Dependencies / assumptions
- Requires the Phase 2 `ThrusterSpec` and `VehicleCommand` types, both
  already in the chat. No new external dependency, no new package.
- All wrenches are expressed in the body's local frame. The caller is
  responsible for rotating them into world space, or for using
  `AddRelativeForce` / `AddRelativeTorque`.
- `CommandWrenchMap.Default` matches the seven-nozzle set produced by the
  private `SixDofBody.CreateDefaultThrusters()`, so an authored vessel can
  start from these numbers and tune rather than entering values blind.
- The allocator is opt-in: existing vehicles keep using the shipped mixer
  and nothing breaks.

### Deferred to later phases
- Optional `SixDofBody` integration flag (e.g. `useControlAllocator`) will
  be added in a future additive pass as a one-line opt-in on the existing
  body — not a rewrite of the Phase 2 mixer, so scene-authored nozzles and
  the legacy behaviour remain valid.
- Sonar / thermal visualisation of the thermocline (still art pass).
- Dive computer that reads `LastSolveSaturated` /
  `LastResidualSquared` while consuming Phase 3's `CockpitEventBus`.

## Entry: Phase 4 — CI/CD (Quest 3 Build & Headless Test Harness)

### Constraints applied
- CONSTITUTION.md isolation honoured: everything lands under
  `oculus-knights/UnityVR/`; nothing references Webtypicon2 or any liturgical
  module, and the workflow triggers only on the `oculus-knights` tree.
- Additive only. No Phase 1, 2 or 3 file is modified. The new `Build/` module
  and the new `Tests/EditMode/` folder stand beside the existing folders and
  only *read* from Phase 1/2/3 (via `BuildStamp.Version` and via reflection);
  no gameplay file needs to change to keep the suite green.
- `reference_repo/` was not touched. The Freeciv insight was again
  non-portable: the supplied links resolve to a 404 badge, a missing
  freeciv.org page and a 2012 forum shutdown notice, so there was no code,
  schema or process artefact to reuse. Phase 4 was authored from the
  CONSTITUTION + HLD alone. (Insight worth recording for the next phase: the
  "Freeciv reference" channel is dead and should not be budgeted for again.)

### Files landed
- `.github/workflows/unity-quest3-ci.yml` — two-stage pipeline
  (`editmode-tests` → `build-quest3`).
- `Assets/Scripts/Build/BuildStamp.cs` — runtime-readable provenance
  (version, channel, commit, UTC), `System`-only.
- `Assets/Scripts/Build/Editor/QuestBuildPipeline.cs` — headless
  `-executeMethod` build entry point; owns every Quest 3 player setting.
- `Assets/Scripts/Build/Editor/BuildStampWriter.cs` — CI stamping of
  `BuildStamp.cs` from `GITHUB_*` environment variables.
- `Assets/Tests/EditMode/BuildStampTests.cs` — stamping-contract tests.
- `Assets/Tests/EditMode/Phase2ApiContractTests.cs` — reflection contract
  tests over the frozen Phase 2 public statics.

### Architectural reasoning
1. **C# owns the build, YAML owns the orchestration.** A pipeline that only
   ever runs in CI is untestable by the people who must fix it. Putting the
   settings and the `BuildPipeline.BuildPlayer` call in an Editor class means
   a developer can reproduce a CI failure locally with the same menu item, and
   means every Quest 3 player setting is a diff in review rather than a
   binary `ProjectSettings.asset` change nobody reads. The YAML is then thin
   enough to survive a runner migration unchanged.
2. **Two stages with a hard test gate.** `build-quest3` declares
   `needs: editmode-tests`. An IL2CPP Android compile is the expensive step
   (tens of minutes on a shared runner, and it consumes the licence seat), so
   it must never run on a red suite. The `Library/` cache is keyed on
   `packages-lock.json` and shared, so the second stage starts warm.
3. **Build stamping, not build guessing.** The recurring failure mode for a
   play-test build is "which commit is this?". `BuildStampWriter` rewrites a
   `System`-only constants file from `GITHUB_SHA` / `GITHUB_RUN_NUMBER` /
   `GITHUB_REF_NAME` before the build, so `BuildStamp.Describe()` — printed by
   the debug HUD — names the commit. The writer emits the *exact byte shape*
   of the committed file so the CI rewrite is a minimal diff, and the
   committed defaults are `local` / `unknown` so a developer build can never
   masquerade as a release. `Application.version` is then set from the same
   stamp, keeping `PlayerSettings` and the HUD in agreement by construction.
4. **Contract tests, not duplicate numerics.** Re-deriving `DensityAt` or
   `SphereSubmergedFraction` in a test would rot the moment the solver is
   tuned, and would duplicate the very code it is meant to protect. What
   actually breaks QA is a *rename*: if `WaterColumn.DensityAt` or
   `SixDofBody.SphereSubmergedFraction` loses `static`, or `VehicleCommand`
   stops being a struct, `InputCommandAdapter` / `CockpitCommandSource` break
   silently and only in-headset. The reflection contract tests assert exactly
   that surface (name, static-ness, return type, struct-ness,
   `IVehicleCommandSource` still the only seam) and nothing about the values.
   Reflection is used *only* because the exact parameter lists are not yet
   frozen in the HLD text; it keeps the file compiling against any Phase 2
   revision so the failure is a readable assertion rather than a compile
   error in the test assembly. Once the signatures are locked, these become
   direct value tests with no new dependency.
5. **`-customBuildPath` is honoured, not assumed.** `game-ci/unity-builder`
   may or may not forward its output path when a custom `buildMethod` is
   used, and it may hand over either a directory or a file. `ResolveOutputPath`
   therefore accepts both shapes and falls back to a project-relative
   `build/Android/`. The workflow then *locates* the APK with `find` instead
   of hard-coding game-ci internals, so an upstream action change cannot
   silently produce an empty artifact.
6. **XR configuration is warned about, not assumed.** The OpenXR loader lives
   in the XR Plug-in Management package's own settings asset; a batch build
   cannot create it and should not silently ship a flat-screen APK. The
   pipeline probes `EditorBuildSettings.configObjects` for
   `XRGeneralSettingsPerBuildTarget` and logs a loud warning (rather than
   failing the build) when it is absent, which keeps a geometry-only CI run
   useful while making the problem impossible to miss.
7. **Editor-folder stripping.** `QuestBuildPipeline` and `BuildStampWriter`
   live under `Editor/` folders and are wrapped in `#if UNITY_EDITOR`, so they
   are removed from the player entirely. Only `BuildStamp` (four constants and
   a getter) survives into the APK, so Phase 4 adds no measurable runtime cost
   and no new XR2 budget line.

### Dependencies / assumptions
- Requires `com.unity.test-framework` (present in the default 2022.3
  template) and the Android Build Support module with IL2CPP on the runner
  image (the game-ci images ship both).
- `QuestBuildPipeline.BuildApk` is the value of `buildMethod:` in the
  workflow; the `-deaconsPathBuildMode ci` custom parameter is currently
  logged and reserved for a future debug/symbol build branch.
- `UNITY_VERSION` is pinned in the workflow env (`2022.3.40f1`) and must track
  `oculus-knights/UnityVR/ProjectSettings/ProjectVersion.txt`. If the project
  moves Unity versions, that single env var is the only change.
- EditMode tests live under `Assets/Tests/EditMode/` *without* an `.asmdef`,
  relying on Unity Test Framework's automatic NUnit / TestRunner references to
  the predefined assemblies. This is deliberate: adding a test asmdef would
  require an asmdef over `Assets/Scripts/` too (asmdefs cannot reference the
  predefined `Assembly-CSharp`), which would be a restructuring of Phase 1–3
  rather than an additive pass. If the project later adopts asmdefs for
  `Assets/Scripts/`, the test folder should get a matching test asmdef in the
  same change.
- `BuildStamp.Version` is bumped manually (currently `0.4.0`) so that
  `PlayerSettings.bundleVersion` stays a reviewed value rather than a
  CI-incremented one; `PlayerSettings.Android.bundleVersionCode` comes from
  `GITHUB_RUN_NUMBER`, which gives monotonically increasing store uploads.

### Deferred to later phases
- PlayMode tests on physical or cloud Quest 3 hardware (the runner has no
  headset or GPU).
- Android App Bundle / asset-pack split (`androidExportType: androidPackage`
  keeps the single-APK side-load path for now).
- Optional `SixDofBody` `useControlAllocator` opt-in (still pending from the
  Phase 2 completion note).
- Dive computer consuming `LastSolveSaturated` / `LastResidualSquared` via
  Phase 3's `CockpitEventBus`.
- Sonar / thermal visualisation of the thermocline (art pass).
- Roblox-side parity for the shared-seed replay harness noted in the Phase 2
  allocator entry (that is Role 1 work, tracked in `HLD_Roblox.md`).

## Entry: Phase 5 — Instruments (Dive Computer)

### Constraints applied
- CONSTITUTION.md isolation honoured: everything lands under
  `oculus-knights/UnityVR/Assets/Scripts/Instruments/`; nothing references
  Webtypicon2 or any liturgical module.
- Additive only. No Phase 1, 2, 3 or 4 file is modified. The new `Instruments/`
  folder and the new test file stand beside the existing folders and only
  *read* from Phase 2 (`SixDofBody`'s public telemetry properties). No existing
  file needs to change to keep the suite green.
- `reference_repo/` was not touched. The Freeciv insight was again
  non-portable — same 404 badge, missing freeciv.org page and 2012 forum
  shutdown notice as the Phase 4 entry. Phase 5 was authored from the
  CONSTITUTION + HLD + the Phase 2 talk-log's declared telemetry surface alone.
  (Reiterating the Phase 4 note: do not budget for the Freeciv channel again.)

### Files landed
- `Instruments/DiveTelemetrySample.cs`    — pure snapshot struct; no Unity,
  no Physics, no Cockpit reference.
- `Instruments/IDiveTelemetrySource.cs`   — the single instrument seam,
  mirroring `IVehicleCommandSource`.
- `Instruments/SixDofTelemetrySource.cs`  — the only Phase 2 → Phase 5 bridge,
  mirroring `InputCommandAdapter` (Phase 1 → Phase 2) and
  `CockpitCommandSource` (Phase 3 → Phase 2).
- `Instruments/DiveComputer.cs`           — classification, filtering, alarm
  arbitration; publishes C# events only.
- `Assets/Tests/EditMode/DiveComputerTests.cs` — scene-free behavioural tests.

### Architectural reasoning
1. **One bridge per boundary, all the way up.** Phase 1 → Phase 2 has exactly
   one adapter (`InputCommandAdapter`); Phase 3 → Phase 2 has exactly one
   (`CockpitCommandSource`); Phase 5 → Phase 2 has exactly one
   (`SixDofTelemetrySource`). The moment a second file starts reaching into the
   solver, retuning the solver stops being a local change. Keeping the rule
   concrete and visible in the folder layout is how it survives a future
   contributor.
2. **The instrument consumes an interface, not the solver.** `DiveComputer`
   depends on `IDiveTelemetrySource` and nothing else, exactly the way
   `SixDofBody` depends on `IVehicleCommandSource`. That is what makes the
   Phase 5 tests possible without a scene: a ten-line in-file fake replaces the
   entire physics stack, and it is what will make the deferred replay /
   training-autopilot work a new source rather than a new dive computer.
3. **Filtered rate, not raw difference.** The first thing a diver notices on a
   bad HUD is a depth-rate number that jumps on every dropped frame.
   `DiveComputer` runs the raw per-frame difference through a
   frame-rate-independent exponential filter, `1 − exp(−dt / τ)`, so the
   displayed rate is a property of the boat rather than of the CPU. XR2 will
   drop frames during an IL2CPP hitch, so this is not cosmetic.
4. **Alarm arbitration is explicit and severity-ordered.** The prototype mode
   is an if-ladder in the renderer; that hides the ordering decision in
   presentation code and makes it impossible to test. Here it is a single
   `ClassifyAlarm` with a documented precedence
   (`ThrusterSaturated` > depth advisories), and it is directly unit-tested.
   Saturation outranks a shallow-water advisory intentionally: authority
   exhaustion can become a loss of control, and that must not be masked.
5. **Reserved allocator fields, not a speculative dependency.**
   `ThrusterSaturated` / `ThrusterResidualSquared` / `ThrusterSaturationPasses`
   exist on the sample and are exactly what the Phase 2 completion note said
   the dive computer would eventually read, but `SixDofTelemetrySource` leaves
   them at their defaults. Filling them now would require the adapter to reach
   into `SixDofBody` for an allocator that is not yet exposed via the deferred
   `useControlAllocator` opt-in — a hidden coupling and a compile risk against
   design that is explicitly not frozen. One line in the adapter fills them the
   moment the opt-in lands.
6. **Change-detecting events only.** `StateChanged` and `AlarmRaised` fire on
   transitions, never every frame. A HUD animation that retriggers on every
   Update is the other classic dive-HUD bug, and it is cheaper to prevent it in
   the model than to dedupe in each of N future panels.
7. **Interfaces cannot be `GetComponent`ed.** Unity's `GetComponent<T>` requires
   `T : Component`, so `DiveComputer` walks
   `GetComponentsInChildren<MonoBehaviour>` once in `Awake` and casts. This runs
   exactly once per component, not per frame, and `DisallowMultipleComponent`
   prevents two computers fighting over one HUD.
8. **No Cockpit dependency, on purpose.** The natural next step is
   `DiveAlarm` → `CockpitEventBus`. That was deliberately *not* taken in this
   pass: `CockpitEvent.cs` has not been read, and writing against a guessed
   event shape is the same speculative-dependency mistake the reserved
   allocator fields avoid. The C# events are the correct seam until the actual
   type is in hand, at which point a two-line bridge file (not an edit to
   `DiveComputer`) consumes them.

### Dependencies / assumptions
- Requires the Phase 2 `SixDofBody` public telemetry properties
  (`DepthMeters`, `SubmergedFraction`, `DensityKgPerCubicMeter`, `BallastFill`,
  `IsSubmerged`) exactly as declared in the Phase 2 talk-log entry above. If
  any of those is renamed, only `SixDofTelemetrySource.cs` needs adjusting —
  the same single-point-of-change property the other two bridges have.
- `DiveTelemetrySample` uses `float` depth with positive = deeper. If Phase 2
  ever switches to a signed altitude convention, the sign flip belongs in the
  adapter (one place), not in every consumer.
- `DiveComputer.Tick(float)` is public specifically so the Phase 5 tests, a
  future replay driver and a fixed-step autopilot can drive it without
  `Update`. `Update` is a thin `Tick(Time.deltaTime)` and nothing else.
- `DefaultExecutionOrder(-50)` puts `DiveComputer` after
  `SixDofTelemetrySource` (-55) so the adapter is resolved and warm on the
  first frame. Neither depends on Physics execution order, so no further
  ordering constraints are introduced.

### Deferred to later phases
- `CockpitEventBus` bridge for `DiveAlarm` / `DiveState`; blocked only on
  `CockpitEvent.cs` being added to the chat so the event shape is known rather
  than guessed.
- Populating the three reserved allocator fields once
  `SixDofBody.useControlAllocator` lands (the Phase 2 completion and Phase 4
  entries both still list this).
- A concrete `DivePanel` HUD binder (`UnityEngine.UI`) — presentation, and
  deliberately outside the classification-and-arbitration module.
- PlayMode tests on physical or cloud Quest 3 hardware (runner has no headset).
- Sonar / thermal visualisation of the thermocline (art pass).
- Roblox-side parity for the shared-seed replay harness (Role 1 work,
  `HLD_Roblox.md`).

### Architectural reasoning
1. **The deferred dependency is now known, so it is taken.** The previous
   entry deliberately did not bridge `DiveAlarm` → `CockpitEventBus` because
   `CockpitEvent.cs` had not been read and writing against a guessed event
   shape is exactly the speculative coupling the reserved-fields rule exists
   to prevent. With the actual type in hand the bridge is a two-file-composition
   problem, not a guess: `DiveCockpitBridge` subscribes to `DiveComputer`'s
   change-only C# events and republishes them. `DiveComputer` itself is not
   touched, so the classification logic and its tests are unaffected.
2. **No dive-specific `CockpitEventType` exists, so `controlId` carries the
   semantics.** The frozen enum has nine members, none instrument-flavoured,
   and `CockpitEvent.cs` is a Phase 3 file this pass must not edit. The nearest
   generic category is `Toggled` — a signal that changed state — and the
   `controlId` string on the existing struct is what it is for: a subscriber
   discriminator. Two well-known ids are declared as public constants on the
   bridge (`dive.state`, `dive.alarm`), so a HUD or audio director matches on
   them instead of hard-coding strings. This is the *lowest-friction* way to
   publish without editing a frozen enum, and it is clearly documented so a
   future pass that *does* own `CockpitEvent.cs` can add real members and
   migrate this bridge's emission in one place.
3. **`control = null` on the telegram is deliberate.** `CockpitEvent.control`
   is typed `ICockpitControl`; an instrument telegram has no physical control
   behind it, and pretending otherwise would force a synthetic control
   component into the scene just to satisfy a field. A null `control` plus a
   non-null `controlId` is a valid and documented state of the struct, and it
   is what the field is designed to support.
4. **The bridge owns a private bus as a fallback.** `CockpitEventBus` is a
   plain C# class, not a `MonoBehaviour`, so it cannot be `GetComponent`ed and
   cannot be `[SerializeField]`ed without a wrapper the bridge is not allowed
   to introduce. The bridge therefore creates its own `CockpitEventBus` in
   `Awake` and exposes it as `Bus`, and `Bind(CockpitEventBus)` swaps in a
   shared bus when one exists. Result: the bridge is self-contained in a bare
   test scene *and* correct in a full cockpit where the manager owns the bus,
   with no dependency on an API this pass has not read.
5. **Allocator diagnostics without a solver dependency.**
   `SixDofTelemetrySource` gains a nullable `ThrusterAllocator` reference fed
   via `Bind(ThrusterAllocator)`. It reads exactly the three public properties
   the Phase 2 completion entry declared (`LastSolveSaturated`,
   `LastResidualSquared`, `LastSaturationPasses`), none of which require the
   deferred `useControlAllocator` opt-in to *exist* — they only require a
   reference to an allocator that has actually been driven. When the solver
   opt-in lands it calls `Bind(allocator)` once, and the previously-flagged
   "one line in the adapter" is done. The adapter still never reaches into a
   `SixDofBody` field that has not been exposed, so no hidden coupling is
   introduced and no compile risk is added against the untouched solver.
6. **The adapter is resilient to a bad allocator state.** If the allocator is
   null, or present but `!IsConfigured` (i.e. `Configure(...)` has not been
   called yet), the three fields are reset to their defaults rather than read.
   Reading `LastSolveSaturated` off an unconfigured allocator would return the
   stale `false` from field initialisation — harmless but a lie — so the guard
   makes the sample honest rather than merely safe.
7. **Unsubscribe on destroy and before rebind.** `DiveComputer` keeps a
   multicast delegate of state/alarm subscribers; a bridge that forgets to
   detach leaves a dangling listener and (worse) double-delivers after a
   rebind. `Unsubscribe` is called both from `OnDestroy` and from
   `Bind(DiveComputer)` before resubscribing, and `DiveCockpitBridgeTests`
   asserts both paths explicitly.

### Dependencies / assumptions
- Requires the Phase 3 `CockpitEvent` / `CockpitEventType` / `CockpitEventBus`
  and Phase 2 completion `ThrusterAllocator` types, both of which are now in
  the chat. No new external package, no new scene asset.
- `CockpitEventBus` is a plain class (not a `MonoBehaviour`), so a shared bus
  must be handed to the bridge via `Bind`; the workflow expects the eventual
  cockpit manager to do this in its own `Awake`. Until then the bridge's private
  fallback bus is what a bare scene or a unit test uses.
- `DiveCockpitBridge` uses `DefaultExecutionOrder(-45)`, i.e. after
  `DiveComputer` (-50) and `SixDofTelemetrySource` (-55), so the computer has
  resolved its own source before the bridge starts subscribing.
- `SixDofTelemetrySource.Bind` is now overloaded on `SixDofBody` and
  `ThrusterAllocator`. Neither type inherits from the other, so there is no
  overload ambiguity; a caller that passes `null` should use the typed overload.
- The allocator's diagnostics reflect the *last* `Allocate` call. A solver that
  allocates only on discrete events (rather than every FixedUpdate) will show a
  stale `LastSolveSaturated`; the same note already appears in the Phase 2
  completion entry and remains the solver's responsibility.

## Entry: Phase 5 (integration) — Shared Bus Auto-Discovery

### Constraints applied
- CONSTITUTION.md isolation honoured: the change stays inside
  `oculus-knights/UnityVR/Assets/Scripts/Instruments/` and its test folder;
  nothing references Webtypicon2 or any liturgical module.
- Additive only. `DiveComputer`, `DiveTelemetrySample`,
  `IDiveTelemetrySource`, `SixDofTelemetrySource`, the Phase 3 cockpit files,
  and everything from Phases 1–4 are NOT modified. `DiveCockpitBridge`
  (a Phase 5 file from the previous entry) is updated in place: it gains
  shared-bus auto-discovery and a small read-only `UsingSharedBus` property,
  and its prior behaviour (private fallback bus, explicit `Bind`) is fully
  preserved.
- `CockpitManager.cs` (Phase 3) is read-only reference material for this pass
  — the same additive rule as `reference_repo/`. It is not edited.
- `reference_repo/` was not touched. The Freeciv insight remained
  non-portable (same dead links as the three previous entries).

### Files landed / changed
- UPD `Instruments/DiveCockpitBridge.cs` — `Awake` now auto-adopts
  `CockpitManager.Instance.Bus` when available; new serialized
  `autoBindSharedBus` toggle; new `UsingSharedBus` read-only property.
- UPD `Assets/Tests/EditMode/DiveCockpitBridgeTests.cs` — three new tests
  (fallback when no manager, adoption when manager present, explicit bind
  wins over adoption); `TearDown` now tears down a manager host as well.
- UPD `HLD_VR.md` — version 0.6.1; §6.8 gains a "Shared-bus auto-discovery"
  paragraph; §6.9 updated to list bus-resolution coverage.
- UPD `talk_log_2026-09-23.md` — this entry.

### Architectural reasoning
1. **Integration beats configuration.** Until this pass, wiring the bridge
   onto the cockpit's bus was a per-scene manual step, and a scene that
   forgot it silently emitted dive telegrams on a private bus nobody
   listened to. With `CockpitManager` in hand the flow is derivable: the
   bridge can *pull* the shared bus rather than having a scene author *push*
   it. Every scene that already has a cockpit manager now gets correct wiring
   for free, and the private fallback becomes the exception (bare tool / test
   scenes) rather than the default.
2. **`[DefaultExecutionOrder]` makes the pull safe.** `CockpitManager` is
   `-95`, the bridge is `-45`; on normal scene load the manager's `Awake`
   (and therefore its static `Instance`) runs first. That ordering is the
   entire reason the auto-pull is not racy, so it is documented in both the
   bridge and the HLD rather than left as implied knowledge.
3. **A null manager is not a failure; a null bus would be.** The bridge
   resolves in a fixed order: explicitly bound bus, then
   `CockpitManager.Instance.Bus`, then a private fallback. The user-facing
   invariant is "`Bus` is never null after `Awake`", which is the same one
   the previous pass established. That is what keeps the bridge usable in a
   unit test with no manager, in a bare tool scene with no manager, in a
   normal gameplay scene with a manager, and in a cutscene that overrides the
   bus for a specific sequence — all with the same source file.
4. **`UsingSharedBus` is observability, not plumbing.** A HUD editor or a
   smoke test wants to know whether they are on the shared channel without
   poking at references. Exposing the answer as a read-only property makes
   that check a one-liner and gives the EditMode test a real assertion
   (`bridge.UsingSharedBus == true`) rather than a reference-equality
   side-proof. It introduces no state: it compares the current external
   reference to `CockpitManager.Instance.Bus` on demand.
5. **The private fallback is still the root, not a legacy path.** The
   previous pass introduced it as a self-containment property, and this pass
   preserves it: a scene with no manager must still be able to test a HUD, a
   cutscene, or an autopilot-driven sequence. Making the shared bus the
   *first* choice, not the *only* choice, is the whole point of a fallback
   ladder instead of a hard requirement.
6. **The test fixture now owns the singleton's lifetime.** Because
   `CockpitManager.Instance` is a static, a fixture that creates one without
   tearing it down leaks state into every later test. `TearDown` therefore
   destroys `managerHost` (which clears `Instance` via the existing
   `OnDestroy` in `CockpitManager`) *before* destroying the bridge host, and
   the two "no manager" / "manager present" tests are paired so each
   demonstrates the intended default of the other.

### Dependencies / assumptions
- Requires `CockpitManager.Instance` and `CockpitManager.Bus` exactly as
  declared in the Phase 3 source added to the chat. If `Bus` is ever moved to
  a nested type or renamed, only `DiveCockpitBridge.AdoptSharedBusIfAvailable`
  and `DiveCockpitBridge.UsingSharedBus` need adjusting — the same
  single-point-of-change property the other bridges have.
- `CockpitManager.Bus` is publicly readable and returns the same instance for
  the lifetime of the manager. The bridge caches it in `externalBus` at
  `Awake`, so a manager that is destroyed *after* the bridge adopts its bus
  leaves the bridge holding a still-live `CockpitEventBus` (the bus itself is
  a plain class, not owned by the manager's GameObject). That is the correct
  behaviour for `persistAcrossScenes = true` and harmless for the default
  scene-local case; it is documented so no future reader mistakes it for a
  leak.
- `autoBindSharedBus` defaults to true, so existing scenes that do have a
  manager will (intentionally) switch from the private bus to the shared bus
  as a result of this change. That is a *behaviour fix*, not a regression:
  the previous bus was one no HUD was subscribed to.
